    목차
      01 · 본질

      LLM의 본질: 다음 Token 맞히기

      가장 중요한 것부터 말씀드리겠습니다.

      LLM (Large Language Model)이 하는 일은 근본적으로 "지금까지의 글 다음에 올 조각이 무엇일지"를 확률로 예측하는 것입니다.

      GPT (Generative Pre-trained Transformer) 계열 모델의 출발점이 된 논문들도 학습 목표를 이렇게 정의합니다. 앞에 나온 Token들이 주어졌을 때 다음 Token의 확률을 최대한 잘 맞히도록 학습시킨다는 것이죠.

      "오늘 아침에 커피를"이라는 문장이 있으면, 모델은 "마셨다"에 높은 확률을, "던졌다"에 낮은 확률을 매깁니다. 하나를 고르고, 그걸 문장 끝에 붙이고, 다시 다음 조각을 예측합니다. 이걸 수백, 수천 번 반복하면 긴 답변이 됩니다. 위의 데모가 바로 그 한 걸음입니다.

      비유

      Smartphone keyboard의 자동완성을 떠올리면 됩니다. 다만 규모가 상상을 초월하게 큰 자동완성입니다.

      물론 "그냥 자동완성"이라고 하면 과소평가입니다. 다음 Token을 잘 맞히려면 문법, 사실, 맥락, 추론 pattern까지 학습해야 하기 때문입니다. GPT-3 논문은 이렇게 학습한 모델이 예시 몇 개만 보여줘도 번역, 질의응답 같은 여러 과제를 해낸다는 것을 보였습니다.

      그럼 여기서 말하는 '조각'은 대체 뭘까요?

      02 · 입력 단위

      Token과 Tokenizer: 모델이 읽는 단위

      모델은 글자를 그대로 읽지 않습니다. 먼저 글을 Token이라는 조각으로 자르고, 각 조각에 번호를 붙입니다. 이 자르는 도구가 Tokenizer입니다.

      Token은 단어일 수도, 단어의 일부일 수도, 글자 하나일 수도 있습니다. 자주 나오는 덩어리는 Token 하나가 되고, 드문 단어는 여러 조각으로 쪼개집니다. 널리 쓰이는 BPE (Byte Pair Encoding)는 자주 붙어 나오는 문자 쌍을 반복해서 하나로 합쳐 가며 Vocabulary를 만듭니다.

      영어
      I love strawberry latte
      한국어
      오늘 아침에 커피를
      Token ID (Identifier)
      403021159781977251766

      자르는 모양을 보여주려고 만든 예시입니다. 실제 경계와 번호는 Tokenizer마다 다릅니다.

      ≈ 4글자영어 text 1 Token (OpenAI 안내)
      ≈ 0.75단어영어 기준 1 Token이 담는 단어 수
      한국어 ↑같은 내용에 Token이 더 드는 편. Tokenizer마다 차이가 큼

      OpenAI 안내에 따르면 일반적인 영어 text에서 1 Token은 대략 4글자, 단어로는 약 0.75단어입니다(출처). 한국어는 보통 같은 내용을 쓰는 데 Token이 더 많이 드는데, Tokenizer마다 크게 다르니 실제 비율은 직접 확인해 보시는 게 좋습니다. 모델이 아는 Token의 전체 목록은 Vocabulary라고 부릅니다.

      이게 실생활에서 왜 중요할까요?

      • API (Application Programming Interface) 요금이 Token 단위로 매겨집니다.
      • Context Window(뒤에서 설명)도 Token 단위입니다.
      • "strawberry에 r이 몇 개냐" 같은 질문에서 모델이 가끔 헤매는 것도, 글자가 아니라 Token 덩어리로 보고 있다는 점과 관련 있다고 흔히 설명합니다.
      03 · 의미 공간

      Embedding: 단어에 좌표 주기

      Token은 번호일 뿐입니다. '커피'가 4521번이고 '차'가 4522번이라고 해서 두 단어가 비슷하다는 뜻은 아니죠. 번호에는 의미가 없습니다.

      그래서 모델은 각 Token을 수백~수천 개의 숫자로 이뤄진 Vector로 바꿉니다. 이걸 Embedding이라고 합니다. Transformer 원 논문은 이 Vector 크기를 512로 썼고, 현재 open-weight 모델 중 가장 큰 Kimi K3는 7,168입니다.

      갑자기 뭔가 어렵죠?

      비유

      지도를 떠올려 보세요. 모든 단어가 거대한 지도 위 어딘가에 점으로 찍혀 있고, 의미가 비슷한 단어끼리 가까이 모여 있습니다.

      비유의 한계실제 '지도'는 2차원이 아니라 수천 차원이고, 각 축이 "성별"이나 "크기"처럼 사람이 이름 붙일 수 있는 의미를 갖는 것도 아닙니다. 좌표 역시 사람이 정해 주지 않습니다. 학습 과정에서 저절로 만들어집니다.
      04 · 모델 크기

      Neural Network와 Parameter: 수십억 개의 Dial

      이제 이 Vector를 받아 "다음 Token 확률"을 계산하는 기계가 필요합니다. 그게 Neural Network입니다. Neural Network의 Neuron은 이름과 달리 뇌세포를 흉내 낸 것이 아닙니다. 숫자를 곱하고 더하는 계산 단위일 뿐입니다.

      Neural Network는 본질적으로 거대한 계산식입니다. 입력 숫자에 어떤 값을 곱하고 더하고 비선형 함수에 통과시키는 일을 수없이 반복합니다. 여기서 "곱하는 값"들이 Parameter, 곧 Weight입니다.

      비유

      거대한 audio mixing console을 떠올려 보세요. Dial이 수십억 개 달려 있고, Dial을 어떻게 돌려 두었느냐에 따라 같은 입력에서 전혀 다른 소리가 나옵니다.

      학습은 이 Dial들을 조금씩 돌려 맞추는 과정입니다.

      GPT-3는 이 Dial이 1,750억 개였습니다. "30B 모델", "70B 모델"이라고 할 때의 B (Billion)가 바로 이 개수입니다. 학습은 이 Dial들을 잘 맞춰 두는 과정이고, 다 맞춘 Dial 설정값 묶음이 우리가 내려받는 Model file입니다.

      음악에는 정답이 없지만 모델의 지능에는 높고 낮음이 있죠. '정답'이 있다고 가정하면, Dial이 많을수록 더 정확한 소리를 뽑을 수 있습니다. 대신 거쳐야 할 계산이 많아지니 계산할 양도 늘어납니다.

      2 bytesDial 하나를 bf16 (bfloat16)으로 저장할 때
      277.8억Qwen3.8-27B 총 Parameter (vision encoder 포함)
      55.6 GBbf16 기준 Weight 용량. 공식 BF16 checkpoint 크기와 일치

      이 크기를 4-bit 근처로 줄이는 작업이 Quantization(양자화)입니다.

      05 · 학습

      학습 방법: Loss, Backpropagation, Gradient Descent

      수십억 개 Dial을 사람이 손으로 맞출 수는 없습니다. 그래서 이렇게 합니다.

      1. Forward Pass

        문장을 넣고, 현재 Dial 상태로 다음 Token 확률을 계산합니다.

      2. Loss

        정답 Token에 매긴 확률이 낮을수록 큰 벌점을 줍니다. 다음 Token 예측에서는 보통 정답 Token 확률의 log에 마이너스를 붙인 값, Cross Entropy를 씁니다.

      3. Backpropagation

        이 벌점에 각 Dial이 얼마나 책임이 있는지, 출력에서 입력 방향으로 거슬러 올라가며 계산합니다. 1986년 Rumelhart, Hinton, Williams의 논문이 이 방법을 널리 알렸습니다.

      4. Gradient Descent

        벌점이 줄어드는 방향으로 모든 Dial을 아주 조금씩 돌립니다.

      으악, 어려워! 움직이는 그림으로 보면 이렇습니다.

      ① Forward Pass② Loss③ Backpropagation④ Gradient Descent

      문장을 넣고 현재 Dial로 다음 Token 확률을 계산합니다.

      step 0 · Loss —

      Dial 하나를 가로축에, Loss를 세로축에 놓은 그림입니다. 실제로는 수십억 차원에서 동시에 일어납니다.

      이걸 수조 개 Token에 대해 반복합니다.

      비유

      안개 낀 산에서 눈을 가리고 골짜기를 찾아 내려간다고 생각해 봅시다. 발밑의 경사만 느끼면서 내리막 쪽으로 한 걸음씩. 경사를 계산하는 게 Backpropagation, 한 걸음 내딛는 게 Gradient Descent입니다.

      06 · 문맥

      Transformer와 Attention: 문맥을 읽는 방법

      여기까지 오면 질문이 생깁니다. "은행"은 "은행나무"와 "은행 대출"에서 뜻이 다르잖아요. 모델은 이걸 어떻게 구분할까요?

      답은 Attention입니다. 2017년 Google 연구진의 논문 「Attention Is All You Need」가 Attention만으로 이뤄진 구조인 Transformer를 제안했고, 이후 거의 모든 LLM의 뼈대가 됐습니다.

      아이디어는 이렇습니다. 각 Token이 문장 안의 다른 Token들을 둘러보고 "지금 내 의미를 정하는 데 누가 중요한가"를 점수로 매긴 뒤, 중요한 Token의 정보를 더 많이 섞어 자기 Vector를 업데이트합니다. 조금 더 구체적으로, 논문은 각 Token에서 Vector 세 개를 만듭니다.

      Q · Query (질문)"나는 이런 정보를 찾고 있어"
      K · Key (색인)"나는 이런 정보를 갖고 있어"
      V · Value (내용)"실제로 건네줄 내용은 이거야"

      Query와 Key가 잘 맞을수록 그 Token의 Value를 많이 가져옵니다.

      Attention"은행"의 문맥 정하기
      비유

      회의실에서 궁금한 걸 들고(Query) 둘러보다가, 그 주제를 아는 사람(Key)에게 귀를 기울이고, 그 사람의 말(Value)을 받아 적는 것과 비슷합니다.

      논문은 이걸 여러 갈래로 동시에 하는 Multi-head Attention도 제안했습니다(원 논문 기본 모델은 Head 8개). 부록의 시각화에서도 Head마다 다른 일을 하는 모습이 보였는데, 문장 구조나 대명사가 가리키는 대상과 관련돼 보이는 Head들이 있었습니다.

      Transformer가 중요했던 또 하나의 이유는 Parallel Processing입니다. 이전에 주로 쓰던 RNN (Recurrent Neural Network)은 단어를 하나씩 순서대로 처리해야 했지만, Transformer는 문장 전체를 한 번에 처리할 수 있어 학습이 훨씬 빨랐습니다. GPU (Graphics Processing Unit)가 비싸진 이유가 이거 하나입니다.

      Multi-headHead 8개가 각자 다른 일
      Parallel하나씩 vs 한 번에
      RNN
      Transformer
      비유의 한계"중요한 단어에 주목한다"는 표현 때문에 모델이 사람처럼 '의도적으로 집중'한다고 오해하기 쉽습니다. 실제로는 Vector끼리의 유사도 점수를 계산해 가중 평균을 내는 연산입니다.
      07 · 구조

      Layer와 Decoder 구조

      점점 어려워지는 것 같기도 하지만…

      Transformer Block 하나는 대략 "Attention → Feed-forward Neural Network"로 이뤄져 있습니다. Attention이 Token끼리 정보를 주고받는 단계라면, Feed-forward는 각 Token이 받은 정보를 혼자 소화하는 단계입니다. 이 Block을 층층이 쌓은 것이 Layer입니다. 아래층은 단순한 pattern을, 위층으로 갈수록 더 추상적인 관계를 다룬다고 흔히 설명합니다.

      비유

      공장의 assembly line입니다. 원재료(Embedding)가 들어와 수십 개 공정(Layer)을 거치며 다듬어지고, 마지막 공정에서 "다음 Token 확률표"라는 완제품이 나옵니다.

      그런데 원래 Transformer는 번역기였습니다. 원문을 읽는 Encoder와 번역문을 쓰는 Decoder, 두 부분으로 되어 있었죠. GPT 계열은 이 중 Decoder 쪽만 가져와 쌓았습니다. 오늘날 ChatGPT, Claude, Llama 같은 대화형 LLM 대부분이 이 Decoder-only 구조입니다. Decoder의 핵심 규칙은 하나입니다.

      각 Token은 자기보다 앞에 있는 Token만 볼 수 있습니다.

      행: 지금 Token · 열: 볼 수 있는 Token. 오른쪽 위(미래)는 가려져 있습니다.

      미래를 훔쳐보지 못하게 가려 둔 것이죠(Masking). 다음 Token을 예측하는 모델이 정답을 미리 보면 안 되니까요.

      08 · Post-training

      Pre-training, SFT, RLHF: 학생에서 비서로

      지금까지 설명한 방식으로 Internet 규모의 text를 학습시키면 Pre-training 모델이 나옵니다. 아는 건 많지만 대화 상대로는 이상합니다. 질문을 던지면 답하는 대신 비슷한 질문을 몇 개 더 써 내려갈 수도 있습니다. 문서 이어 쓰기를 배웠지, 질문에 답하기를 배운 건 아니니까요.

      같은 질문다른 반응
      Pre-training만 한 모델
      커피를 맛있게 내리는 방법은?

      ✕ 답 대신 비슷한 질문을 이어 씀

      SFT + RLHF를 거친 모델
      커피를 맛있게 내리는 방법은?

      ✓ 질문에 답하는 형식과 태도를 배움

      답변 문구는 설명용 예시입니다.

      그래서 두 단계를 더 거칩니다. OpenAI의 InstructGPT 논문이 이 과정을 잘 정리했습니다.

      1. SFT (Supervised Fine-Tuning)

        사람이 직접 쓴 "질문–모범 답변" 예시로 추가 학습합니다. 질문을 받으면 답하는 형식을 배웁니다.

      2. RLHF (Reinforcement Learning from Human Feedback)

        모델이 쓴 여러 답변을 사람이 순위 매기고, 그 선호를 배운 Reward Model을 만든 뒤, Reward 점수가 높아지도록 원래 모델을 강화학습으로 조정합니다.

      RLHF네 걸음
      ①

      답변 여러 개 생성

      답변 A답변 B답변 C

      같은 질문에 SFT 모델이 답변을 여러 개 씁니다.

      ②

      사람이 순위 매기기

      123답변 A답변 B답변 C

      더 나은 순서로 정렬. A > C > B

      ③

      Reward Model 학습

      A0.9
      C0.6
      B0.2

      사람의 선호를 점수로 흉내 내는 모델.

      ④

      강화학습으로 조정

      Reward가 높아지도록 원래 모델을 조정. InstructGPT는 PPO (Proximal Policy Optimization) 사용.

      결과가 인상적이었습니다. 사람 평가자들은 RLHF를 거친 13억 Parameter InstructGPT의 답변을, 100배 이상 큰 1,750억 Parameter GPT-3의 답변보다 더 선호했습니다. (전설의 시작)

      GPT-31,750억
      InstructGPT (RLHF 적용)13억
      100배 이상 작지만 사람들이 더 선호
      비유

      Pre-training은 도서관 책을 전부 읽은 박식한 학생이고, Fine-tuning과 RLHF는 그 학생에게 손님 응대하는 법을 가르치는 신입 연수입니다. 지식을 새로 넣는다기보다 이미 가진 지식을 어떤 태도와 형식으로 꺼낼지 다듬는 쪽에 가깝습니다.

      주석요즘은 RLHF 말고도 다양한 Post-training 기법이 쓰이며, 각 회사가 구체적인 방법을 모두 공개하지는 않습니다.

      • 엄청난 연산. 우리가 할 일은 별로 없습니다
      추론 · Inference공장 돌리기
      • 고정된 Dial로 답을 만드는 과정
      • Forward Pass만. Backpropagation도 Weight 업데이트도 없음
      • 맨날 합니다. ChatGPT와의 대화는 전부 Inference

      흔한 오해: 대화 중에는 배우지 않는 모델

      ChatGPT와 나누는 대화는 전부 Inference입니다. 대화 중에 모델이 "학습"되고 있는 게 아닙니다. 모델이 내 말을 기억하는 것처럼 보이는 건, 대화 내용 전체가 매번 입력(Context)으로 다시 들어가기 때문입니다.

      Request 1
      System질문 1
      Request 2
      System질문 1답 1질문 2
      Request 3
      Sys질문 1답 1질문 2답 2질문 3
      ModelDial 그대로 · 매번 전체를 처음부터 다시 읽음

      파란 테두리가 이번에 새로 쓴 부분입니다. 나머지 기록은 매번 다시 보냅니다.

      대화 기록이 service 개선용 학습 data로 쓰일지는 각 service 정책의 문제이고, 그 대화 순간에 Dial이 바뀌지는 않습니다.

      비유

      Training은 공장을 짓고 기계를 세팅하는 일, Inference는 다 지은 공장을 돌려 제품을 찍어내는 일입니다. 지난 글의 "Mac에서 local로 돌린다"는 이야기는 전부 Inference 이야기였습니다.

      10 · Inference의 두 박자

      Prefill과 Decoding: Inference의 두 박자

      Prefill
      Decoding
      ChatGPT에 긴 문서를 붙여 넣으면
      Prefill · 잠깐 멈칫Decoding · 흘러나옴

      Prefill은 Prompt Token을 한꺼번에 처리하고(연산력 병목), Decoding은 Token을 하나씩 순서대로 만듭니다(Memory Bandwidth 병목).

      ① Prefill

      내 Prompt 전체를 한꺼번에 모델에 통과시키는 단계입니다. Prompt Token은 이미 다 주어져 있으니 동시에, 병렬로 처리할 수 있습니다. GPU의 병렬 연산을 효율적으로 쓰는 단계라 계산량이 많고, 속도는 연산력이 좌우합니다.

      ② Decoding

      답을 한 Token씩 만드는 단계입니다. 1장에서 말했듯 Token 하나를 뽑아야 다음 Token을 예측할 수 있으니 본질적으로 순차적입니다. vLLM 논문은 이 단계가 병렬화가 어렵고 matrix-vector 곱 위주라 GPU 연산력을 다 쓰지 못하는 memory-bound 단계라고 설명합니다. 그래서 속도는 계산 능력보다 Memory Bandwidth에 더 크게 좌우됩니다(자세한 건 지난 글 참고).

      ChatGPT에 긴 문서를 붙여 넣으면 첫 글자가 나오기까지 잠깐 멈칫하고(Prefill), 그다음엔 일정한 속도로 글자가 흘러나오죠(Decoding). 그 두 박자입니다.

      11 · Memory

      KV Cache: 이미 읽은 건 다시 읽지 않기

      Decoding에는 낭비가 숨어 있습니다. Token을 하나 새로 만들 때마다 앞의 모든 Token에 대해 Attention을 계산해야 하거든요. 앞 Token들의 Key와 Value(6장)를 매번 처음부터 다시 계산한다면 엄청난 중복입니다.

      그래서 한 번 계산한 Key와 Value를 Memory에 저장해 두고 재사용합니다. 이게 KV (Key-Value) Cache입니다. 새 Token은 자기 Query만 계산해서 저장된 Key, Value와 비교하면 됩니다.

      비유

      시험공부할 때 이미 읽은 chapter의 요점 Note를 만들어 두는 것과 같습니다. 새 chapter를 읽을 때마다 앞 chapter를 처음부터 다시 읽지 않고 Note만 펼쳐 보면 되죠.

      대가는 Memory입니다. 대화가 길어질수록 Note도 두꺼워집니다.

      그래서 모델 설계자들은 KV Cache를 줄이려고 애씁니다.

      12 · 비용

      Prompt Caching: 남이 만든 요점 Note 빌려 쓰기"Cache는 왜 할인해요?"

      API 요금표를 보면 Cached Input 가격이 따로 있고, 일반 입력보다 훨씬 쌉니다. 같은 Token인데 왜 값이 다를까요? 답은 11장의 요점 Note에 있습니다.

      ① 원리: 같은 앞부분이면 Note 재사용

      KV Cache는 한 번의 Request 안에서 쓰는 요점 Note라고 했습니다. 그런데 Request가 끝나면 그 Note는 보통 버려집니다. 다음 Request가 오면 Prefill(10장)부터 다시, Prompt 전체의 Key·Value를 처음부터 계산하죠.

      그런데 많은 Request는 앞부분이 똑같습니다. 같은 System Prompt, 같은 Tool 정의, 같은 참고 문서를 매번 맨 앞에 붙이니까요. 그렇다면 공통 앞부분(Prefix)의 Note는 보관해 뒀다가 다음 Request에서 그대로 꺼내 쓰면 됩니다. 이게 Prompt Caching (Prefix Caching)입니다.

      Request A
      ToolsSystem참고 문서질문 A
      Write
      Request B
      ToolsSystem참고 문서질문 B
      Hit
      Timestamp 넣은 Request
      09:52ToolsSystem참고 문서질문
      Miss

      공통 Prefix(초록)는 Cache에서 꺼내 쓰고, 맨 앞이 바뀌면 전부 다시 계산합니다.

      OpenAI도 정확히 이렇게 설명합니다. 입력을 처리하며 만든 중간 상태, 곧 Key·Value를 재사용 가능한 Prefix에 대해 보관해 두고, 다음 Request가 같은 Prefix를 가지면 그 Token을 다시 처리하지 않고 저장된 상태를 쓴다는 것이죠. 저장하는 건 Token 자체가 아니라 KV Tensor라고 명시합니다. Open-source serving engine vLLM의 'Automatic Prefix Caching'도 같은 원리로 공유된 Prefix의 계산을 건너뜁니다.

      그래서 할인의 이유는계산을 안 했으니 덜 받는 겁니다.

      Cache를 맞힌 부분은 Prefill 연산을 건너뛰고, 그만큼 첫 글자가 나오기까지의 시간 (TTFT, Time To First Token)도 줄어듭니다.

      ② Cache Hit와 Cache Miss

      • Cache Hit: 보관된 Note 중 내 Request의 앞부분과 똑같은 게 있어서 꺼내 쓴 경우. 그 부분은 할인된 가격으로 계산됩니다.
      • Cache Miss: 맞는 Note가 없어서 처음부터 계산한 경우입니다.

      처음 보내는 Prefix라 저장된 Note가 없을 때

      MISS 2

      유효 기간이 지남

      TTL (Time To Live)이 지나 Note가 버려졌을 때

      MISS 3

      앞부분이 조금이라도 다름

      Prefix가 한 글자라도 달라졌을 때

      핵심은 "조금이라도"입니다. Anthropic 문서는 Cache Hit가 나려면 Cache 지점까지의 text와 이미지가 100% 똑같아야 한다고 씁니다. OpenAI도 rendering된 Prefix 전체가 일치해야 재사용된다고 설명합니다.

      Cache Hit를 내는 실전 팁

      TIP 1

      안 바뀌는 건 앞에, 바뀌는 건 뒤에

      System Prompt, Tool 정의, 참고 문서처럼 고정된 부분을 맨 앞에 두고, 사용자 질문처럼 매번 달라지는 부분은 맨 뒤에 둡니다. 세 회사 문서가 모두 같은 조언을 합니다. Anthropic은 Cache Prefix가 tools → system → messages 순서로 만들어지고, 앞 단계가 바뀌면 그 뒤가 모두 무효가 된다고 설명합니다.

      TIP 2

      Prefix를 Byte 단위까지 똑같이

      가장 흔한 실수는 System Prompt 맨 앞에 현재 시각: 2026-10-23 09:52 같은 값을 넣는 겁니다. 매 Request 첫 줄이 바뀌니 Note를 한 장도 못 씁니다. OpenAI는 Timestamp나 사용자별 내용을 Prefix 끝으로 옮기라고 하고, Anthropic도 Timestamp가 들어간 블록에 Cache 지점을 두면 쓰기 비용만 내고 읽기는 한 번도 못 한다고 경고합니다.

      Tool 정의의 순서나 Schema를 바꾸는 것, 일부 언어에서 JSON (JavaScript Object Notation) key 순서가 무작위로 바뀌는 것도 Cache를 깹니다. Tool을 잠시 끄고 싶다면 정의를 지우지 말고 tool_choice: "none" 등으로 막으라는 게 OpenAI의 권고입니다.

      TIP 3

      최소 길이를 넘기세요

      너무 짧은 Prefix는 아예 Cache되지 않습니다.

      • OpenAI: GPT-5.6 이후 1,024 Token (이전 모델은 Request 설정에 따라 다름)
      • Anthropic: 모델에 따라 512~4,096 Token. 더 짧으면 cache_control을 붙여도 오류 없이 Cache 없이 처리
      • Gemini: 2.5 Flash·Pro는 2,048 Token, 이후 모델은 4,096 Token
      TIP 4

      TTL (Time To Live) 안에 다시 쓰세요

      Note에는 유통기한이 있습니다.

      • Anthropic: 기본 5분, 쓸 때마다 무료로 갱신. 1시간 옵션은 추가 요금
      • OpenAI: API는 최대 12시간, Codex login 시 영구 보관
      • Gemini: "비슷한 Prefix의 Request를 짧은 시간 안에 보내라"고만 권장
      한 줄 요약안 바뀌는 건 앞에 두고, 한 글자도 건드리지 마세요.
      13 · 한계

      Context Window: 책상의 크기

      Context Window는 모델이 한 번에 볼 수 있는 Token의 최대 개수입니다. 내 Prompt, 대화 기록, 첨부 문서, 그리고 모델이 생성하는 답변까지 모두 이 안에 들어가야 합니다.

      비유

      책상 크기라고 생각하면 됩니다. 책상이 넓으면 자료를 많이 펼쳐 놓고 일할 수 있지만, 넘치는 건 책상 밖으로 밀려납니다.

      다만 책상이 넓어지면 비용도 따라옵니다. Attention은 모든 Token 쌍을 비교하므로 Context가 길수록 계산이 늘고, KV Cache도 커집니다(11장). 긴 Prompt일수록 Prefill이 오래 걸리는 이유입니다.

      14 · 효율

      MoE: 전문가 여러 명 중 몇 명만 부르기

      마지막으로, 요즘 자주 보이는 MoE (Mixture of Experts)를 간단히 짚겠습니다.

      일반 모델(Dense)은 Token 하나를 처리할 때 모든 Parameter를 씁니다. MoE는 Feed-forward 부분을 여러 '전문가'로 나누고, Router가 Token마다 그중 몇 개만 골라 쓰게 합니다.

      Router ← Token "은행" · top-2 of 8
      E1E2E3E4E5E6E7E8

      Mixtral 8x7B: Layer마다 전문가 8개, Token마다 2개만 씁니다. 전체 Parameter는 470억 개지만 Token 하나에 실제로 쓰는 건 130억 개입니다.

      비유

      종합병원과 비슷합니다. 병원에는 전문의가 수십 명 있지만, 환자 한 명은 접수처(Router)의 안내에 따라 필요한 과 두어 곳만 들릅니다.

      전체 전문가를 Memory에 올려 둬야 하니 용량은 크게 필요하지만, Token마다 읽어 오는 양은 적으니 Bandwidth 부담은 작습니다.

      비유의 한계'전문가'라는 이름과 달리 각 전문가가 "의학", "법률"처럼 사람이 알아볼 수 있는 주제를 맡지는 않습니다. Mixtral 논문도 전문가 배정이 주제보다는 문법적·구조적 pattern과 더 관련 있어 보인다고 보고했습니다.
