    01 · Demo vs Platform

    도구를 부를 줄 아는 것과 끝까지 해내는 것은 다르다

    요즘 많은 사람이 AI Agent를 만들지만 여전히 초보적인 단계에 머물러 있습니다. LLM 하나를 연결하고, Tool 몇 개를 설정하고, MCP로 외부 서비스를 붙인 뒤 Prompt 하나로 모델이 스스로 계획하고 도구를 호출하게 하면 완성된 Agent 시스템을 만들었다고 생각합니다.

    실제 기업 운영 환경으로 나아가면 사정이 달라집니다. Agent Demo의 핵심은 모델이 작업을 한 번 해내게 하는 것입니다. 반면 진짜 Agent Platform은 작업 전 과정에서 권한, 상태, 스케줄링, 기억, 신뢰성, 관측 가능성, 그리고 장애가 난 뒤의 복구를 반드시 풀어야 합니다.

    데모와 플랫폼을 나란히 놓으면
    Agent DemoAgent Platform
    목표모델이 작업을 한 번 해내게 한다작업을 매번 안정적으로 끝낸다
    구성LLM 하나 · Tool 몇 개 · MCP 연결 · Prompt 하나오케스트레이션 · 권한 · 상태 · 스케줄링 · 기억 · 관측
    실패하면처음부터 다시 실행어디서 멈췄는지 알고 그 지점부터 복구
    경쟁력모델 추론 능력 · 연결한 MCP 서버 수Agent Runtime과 Harness의 엔지니어링 역량
    판단

    작성자는 앞으로의 AI Agent 경쟁이 누구의 모델이 더 잘 추론하는지, 누가 더 많은 MCP Server를 연결하는지에 머물지 않고, 점차 Agent Runtime과 Harness 전체의 엔지니어링 역량으로 옮겨 갈 것이라고 봅니다.

    02 · Orchestration

    한 번 실행하고 끝이 아니라, 계속 도는 루프

    진짜 Agent는 Prompt를 한 번 실행하고 도구 몇 개를 부른 뒤 끝나지 않습니다. Plan, Act, Observe 사이를 계속 순환하며, 도구가 돌려준 결과를 바탕으로 다음 행동을 다시 판단합니다.

    필요하면 작업을 여러 하위 Agent에게 나눠 맡기고, 그러는 동안 컨텍스트, 실행 상태, 재시도, 예외 복구를 함께 관리해야 합니다. 이것이 오케스트레이션 계층이 하는 일입니다.

    오케스트레이터가 붙잡고 있어야 하는 것
    컨텍스트 관리무엇을 모델에 넘기고 무엇을 덜어 낼지
    실행 상태지금 몇 번째 단계이고 무엇이 끝났는지
    재시도 · 예외 복구실패한 호출을 다시 할지, 다른 길로 갈지
    하위 Agent 위임일을 나눠 맡기고 결과를 다시 모으기

    2.1하위 Agent가 많다고 더 똑똑해지지 않는다

    흔한 오해는 하위 Agent가 많을수록 시스템이 더 똑똑해진다고 생각하는 것입니다. 실제로 여러 Agent가 동시에 일하면 오히려 늘어나는 비용이 있습니다.

    Agent를 늘리면 함께 늘어나는 것, 그리고 일을 나누는 기준
    컨텍스트 전달상태 동기화실행 충돌스케줄링 비용
    결정론적 Workflow에 맡길 것
    순서와 조건이 정해진 일
    • 입력이 같으면 결과도 같아야 하는 단계
    • 규칙으로 분기할 수 있는 처리
    • 정해진 API를 정해진 순서로 부르는 일
    모델(Agent)에 맡길 것
    동적 판단이 필요한 일
    • 도구 결과를 보고 다음 행동을 정해야 할 때
    • 입력이 모호하거나 예외가 많은 부분
    • 규칙으로 미리 다 적을 수 없는 불확실성
    판단

    결정론적 Workflow만으로 끝낼 수 있는 일이라면 여러 Agent를 억지로 들일 필요가 전혀 없습니다. 모델에게 맡길 것은 동적 판단과 불확실성 처리가 필요한 부분이지, 모든 단계를 자율 의사결정으로 포장하는 것이 아닙니다.

    03 · Tools & Permission

    자율 의사결정이 무제한 권한을 뜻하지는 않는다

    MCP의 가치는 Agent가 표준 인터페이스로 외부 도구를 발견하고 호출할 수 있게 한다는 데 있습니다. 하지만 MCP 자체가 도구 호출의 안전성과 신뢰성까지 보장해 주지는 않습니다.

    GitHub, 데이터베이스, 파일 시스템, 사내 업무 시스템에 접근할 수 있는 Agent에 권한 경계가 없다면 매우 위험합니다. 그래서 진짜 Agent Platform에는 독립된 Permission Engine이 있어야 하고, 모든 고위험 작업마다 권한을 검사해야 합니다.

    위험도에 따라 다른 통제
    낮음
    데이터 읽기조회 · 검색
    읽기 권한 범위 안에서 허용
    중간

    읽기와 다른 권한 · 작업마다 정책 검사
    높음
    파일 삭제 · 명령 실행 · 이메일 발송 · 운영 DB 수정
    명확한 제한과 사람의 승인
    판단

    Agent는 자율 의사결정 능력을 가질 수 있지만, 자율 의사결정이 무제한 권한을 뜻하는 것은 아닙니다.

    04 · Memory & Task State

    4.1업로드에서 실패했다면, 업로드부터 다시

    디지털 휴먼 Agent가 낭독 원고 생성, 디지털 휴먼 영상 생성, 자막 처리, 영상 패키징, 파일 업로드, 최종 전달을 해야 한다고 해 봅시다. 이 과정은 여러 외부 API를 거치며 몇 분씩 이어질 수 있습니다. 업로드 단계에서 실패하면 시스템은 앞의 어떤 단계가 이미 끝났는지 알아야 합니다. 디지털 휴먼을 다시 생성하고, API 비용을 다시 청구당하고, 작업 전체를 처음부터 다시 돌려서는 안 됩니다.

    4.2다시 해도 되는 일과 이미 일어난 일

    신뢰할 수 있는 Agent 시스템은 어떤 작업은 안전하게 다시 시도할 수 있고, 어떤 작업은 이미 외부에 부작용을 남겼는지 분명히 구분합니다. 그리고 멱등 키, 작업 상태, 보상 메커니즘으로 중복 실행을 피합니다.

    05 · Observability & Evaluation

    06 · Gateway & Governance

    Agent가 수십 개가 되면 공통 길목이 필요하다

    마지막으로 쉽게 놓치는 부분이 Agent Gateway와 통합 거버넌스입니다. 기업에 Agent가 하나뿐일 때는 많은 문제를 간단한 코드로 풀 수 있습니다.

    하지만 영업, 고객 지원, 콘텐츠 생성, 연구개발, 데이터 분석을 맡는 Agent가 수십 개로 늘어나면 통합 인증, Agent Registry, 모델 라우팅, 도구 등록, 권한 정책, 버전 관리와 감사가 실제로 필요해집니다.

    여러 Agent가 하나의 길목을 지나 같은 기반을 쓴다

    권한 정책리소스 경계
    버전 관리 · 감사누가 무엇을 바꿨나

    이때 비로소 Agent Platform의 가치가 드러납니다. 여러 Agent를 한데 모아 두는 데 그치지 않고, 서로 다른 Agent가 인프라를 재사용하면서 명확한 권한과 리소스 경계 안에서 작업을 끝내도록 통합된 실행·거버넌스 체계를 제공하는 것입니다.

    07 · From Demo to Production

    운영에서 터지는 여섯 가지와 먼저 답할 질문

    많은 Agent 프로젝트는 데모에서는 인상적이지만, 실제 업무에 붙이면 작업 중단, 상태 유실, 중복 실행, 권한 충돌, API 속도 제한, 컨텍스트 오염을 만나면서 시스템 전체의 신뢰성 문제가 드러납니다.

    7.1새 모델 API보다 먼저 답할 질문

    작성자는 AI Agent 엔지니어링에서 깊이 연구할 가치가 있는 것이 Prompt Engineering, Function Calling, MCP만이 아니라 Agent 시스템 전체의 소프트웨어 엔지니어링 문제라고 봅니다. 이 질문들은 새 모델 API를 연결하는 것보다 더 중요할 수 있습니다.

    2. Q2

    ◎ · Summary

    모델은 상한을, 엔지니어링은 납품 가능성을 정한다

    모델은 Agent 능력의 상한을 정하고, Orchestration, Runtime, Memory, Permission, Observability, Evaluation은 그 능력이 실제로 납품 가능한 시스템이 될 수 있는지를 정합니다. 성숙한 Agent는 도구를 얼마나 많이 자율적으로 부르느냐가 아니라, 실제 업무의 제약 안에서 꾸준하고 믿을 수 있으며 통제 가능한 방식으로 작업을 끝내느냐로 판단됩니다.

    01
    실행 가능

    Plan → Act → Observe를 돌리되, Workflow로 될 일은 Workflow로 둔다.

     02
    복구 가능

    작업 상태 · Checkpoint · 멱등 키로 실패 지점부터 재개한다.

     03
    검증 가능

    Trace로 원인을 가르고, 바꿀 때마다 회귀 평가를 돌린다.

     04
    진화 가능

    Gateway · Registry · 권한 정책으로 Agent가 늘어도 경계를 지킨다.
    판단

    앞으로 가치 있는 AI 애플리케이션 엔지니어와 FDE는 모델을 호출하고, Workflow를 구축하고, MCP를 설정하는 데서 그치지 않고 이 역량들을 실행 가능하고, 복구 가능하고, 검증 가능하며, 계속 진화할 수 있는 엔지니어링 체계로 묶어 낼 수 있어야 합니다. Agent Demo와 Agent Platform 사이에 놓인 것은 더 많은 Prompt도, 더 많은 하위 Agent도 아닌 소프트웨어 엔지니어링 역량 그 자체입니다.
