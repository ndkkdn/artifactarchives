01 · Loop in Practice

Addy Osmani와 실전 루프의 구성 요소

CASE 1 · ADDY OSMANI의 실전 운용

하루 5~10개 에이전트 · 80k+ 스타 PR 자동화

  • 작업 공간 분리: Git Worktree로 충돌 없이 병렬 작업
  • 지식 재사용: 스킬(Skills)로 프로젝트 규칙·검증 절차 명문화
  • 외부 메모리: 마크다운·이슈 보드에 상태를 남겨 다음 실행으로 인계
  • 작성자 ≠ 검증자: 생성 에이전트와 판정 에이전트 분리
CASE 2 · CLAUDE CODE 내장 루프

목표 기반 /goal vs 시간 기반 /loop

  • /goal (목표 기반): Lighthouse ≥ 92, LCP < 1.8s 같은 결정론적 수치 충족 시까지 반복
  • /loop (시간 기반): 5분마다 PR·CI 확인 (세션 범위 · 7일 후 만료)
  • /schedule + auto mode: 클라우드 상시 실행과 병렬 worktree 버그 수정
  • 한계: “UI가 예뻐질 때까지” 같은 주관적 취향은 루프 부적합

02 · Why Graph Emerges

Loop 하나로 부족할 때, Graph가 자연히 생긴다

🔀

병렬 분기 (Parallel)

여러 감사 Agent가 동시에 PR을 다각도로 검사

🔎

필터링 · 인계 (Handoff)

Verifier가 발견 사항을 검증해 실제 문제만 Fixer로 인계

03 · What Actually Changed

Graph는 오래됐다 — 달라진 것은 노드

Workflow Engine→DAG Scheduler→State Machine→Airflow
확률적 Agent 노드
① 지시를 잘못 이해할 수 있음 ② 같은 입력에도 다른 결정 ③ 예상 못한 도구·경로 선택
고정 규칙 노드 (Deterministic) vs 확률적 실행자 (Probabilistic)branching 0

작은 작업은 하나의 Chat Context가 제어하지만, 여러 시간·저장소·Agent에 걸치면 명시적 통제가 필요해집니다.

2. 상태 전달

06 · Verification Trap

Agent끼리 합의해도 검증이 되지 않는다

FALSE CONSENSUS

Multi-Agent Self-Review Report

동일 모델 사용: 편향과 추론 맹점을 모든 리뷰어가 공유
동일 컨텍스트: 잘못된 전제가 그대로 다음 노드로 전파
규칙 확인 한계: evaluator는 명시적 규칙만 볼 뿐 품질 미보장
결론 합치 착시: 체계적으로 정리된 잘못된 결과를 승인
SOLUTION 1 · 판단 구조의 분리

① 서로 다른 모델을 Reviewer로 투입
② Reviewer에게 새로운(독립된) 컨텍스트 제공
③ 중요 변경에는 사람의 검토·Veto 유지

SOLUTION 2 · 시스템 외부의 독립된 실제 증거
✔ 실제로 실행된 테스트
✔ 완료된 실제 거래
✔ 사용자의 실제 행동
✔ 독립 전문가의 판단
Correlated Error상관된 오류 · 같은 모델·컨텍스트를 공유하는 에이전트들이 동일한 실수를 반복하는 현상
